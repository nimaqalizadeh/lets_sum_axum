# Middlewares

## The goal

We already have a working handler that greets a user: given a name, it returns `"Hello, Alice!"`. That's the **business logic**, and it works fine on its own.

Now we want to add something that has **nothing to do with the greeting itself**: every time a request comes in, we want to print a log line *before* the handler runs, and another log line *after* the handler returns. Something like:

```text
>>> INCOMING REQUEST: Request { method: GET, path: "/hello", name: "Alice" }
<<< OUTGOING RESPONSE: Ok("Hello, Alice!")
```

We could just paste two `println!` calls inside `HelloHandler` and call it a day. But:

- We will have many handlers (`/users`, `/posts`, `/comments`…) and would have to paste the same logging code into every one of them.
- Logging is not the handler's job. The handler should stay focused on greeting users; logging, auth, rate-limiting, etc. are *cross-cutting concerns* that belong somewhere else.

The clean solution is **middleware**: a separate piece of code that **wraps** the handler from the outside. It runs *before* and *after* the handler, without the handler knowing it exists. In Axum (via Tower), the tools for building middleware are the **`Service`** and **`Layer`** traits.

### Logging is just the first example

We are using logging because it is the easiest thing to demonstrate — a single `println!` makes the *before* and *after* hooks obvious. But the same wrapping pattern handles every cross-cutting concern in a real server:

| Middleware | What it does *before* the handler | What it does *after* the handler |
| --- | --- | --- |
| **Logging** | Print the incoming request | Print the outgoing response |
| **Authentication** | Read the `Authorization` header; reject with `401` if invalid | (nothing) |
| **Rate limiting** | Check the client's request count; reject with `429` if over quota | Increment the counter |
| **Compression** | (nothing) | Gzip the response body |
| **Timeout** | Start a timer | Cancel if the handler takes too long |
| **CORS** | Reject disallowed origins | Add `Access-Control-*` headers |
| **Tracing / metrics** | Start a span / timer | Record duration, attach status code |

Every one of these is built the same way: a wrapper struct that holds an `inner` service, a `call` method that does something *before* `self.inner.call(req).await` and something *after*, plus a tiny `Layer` factory to plug it into the router. Once the logging example clicks, you have learned the pattern for **all of them**.

> **What is "inner"?**
> In the simplest case, `inner` is the **handler** itself (e.g. `HelloHandler`). But "inner" really means *whatever Service is one step closer to the work*. In our chapter, we will call `.layer(LoggingLayer)` on the whole **router**, so `inner` will be the `Router`, which then dispatches to `HelloHandler`. And if we stacked another middleware like `.layer(AuthLayer).layer(LoggingLayer)`, then `LoggingService`'s `inner` would be the `AuthService` — middlewares can wrap middlewares. Anything that implements `Service<Request>` can be the `inner`.

This chapter shows exactly how those two traits, plus the `Router`, fit together to make the snippet at the bottom of this introduction work. We will:

1. Meet the three characters and write each one's code.
2. See how `.layer(...)` actually wraps the router.
3. Open the hood and watch what the compiler does with the generic `S`.
4. Trace a real request from the socket all the way back to the browser.

By the end you should be able to read this snippet and know exactly what happens, line by line:

```rust
// 1. Create the router, add a route, wrap it in our layer.
let app = Router::new()
    .route("/hello", get(HelloHandler))
    .layer(LoggingLayer);

// 2. Start the server.
axum::Server::bind(&"0.0.0.0:3000")
    .serve(app.into_make_service())
    .await;
```

The three characters:

- **`HelloHandler`** — the **Worker** that does the actual job.
- **`LoggingService<S>` / `LoggingLayer`** — the **Guard** that wraps the Worker.
- **`Router`** — the **Dispatcher** that decides which Worker handles which path.

## Warmup: the same pattern with no async, no `Result`, no `Future`

Before we meet the real `Service<Request>` trait — which is generic, asynchronous, returns a `Result`, and has multiple associated types — here is **the whole chapter's pattern** stripped to its bones. No async. No `Pin`. No `Result`. No `Future`. Just plain synchronous Rust.

If the ~50 lines below click, the rest of the chapter is just bolting async and error handling onto the exact same shape.

```rust
// === THE TWO TRAITS — one method each ===

// A "Service" is just a thing that takes a request and produces a response.
trait MiniService {
    fn handle(&self, req: &str) -> String;
}

// A "Layer" is just a thing that wraps an inner Service to produce a new one.
trait MiniLayer<S> {
    type Wrapped: MiniService;
    fn wrap(&self, inner: S) -> Self::Wrapped;
}

// === THE WORKER — does the real work ===

struct HelloHandler;
impl MiniService for HelloHandler {
    fn handle(&self, req: &str) -> String {
        format!("Hello, {}!", req)
    }
}

// === THE WRAPPER — runs BEFORE, delegates to inner, runs AFTER ===

struct LoggingService<S> { inner: S }

impl<S: MiniService> MiniService for LoggingService<S> {
    fn handle(&self, req: &str) -> String {
        println!(">>> {}", req);                  // BEFORE
        let response = self.inner.handle(req);    // PASS DOWN
        println!("<<< {}", response);             // AFTER
        response                                   // RETURN
    }
}

// === THE FACTORY — produces a LoggingService around any inner Service ===

struct LoggingLayer;
impl<S: MiniService> MiniLayer<S> for LoggingLayer {
    type Wrapped = LoggingService<S>;
    fn wrap(&self, inner: S) -> Self::Wrapped {
        LoggingService { inner }
    }
}

// === THE MEETING ===

fn main() {
    let handler = HelloHandler;             // the worker
    let layer   = LoggingLayer;             // the factory
    let app     = layer.wrap(handler);      // wrap = LoggingService { inner: handler }

    let out = app.handle("Alice");
    println!("FINAL: {}", out);
}
```

Run it; the terminal prints:

```text
>>> Alice
<<< Hello, Alice!
FINAL: Hello, Alice!
```

Three things to notice — they are the whole pattern:

1. **`MiniService` is one method.** `handle(req) -> response`. A "service" is just a thing that takes a request and returns a response. Nothing more.
2. **`LoggingService<S>` is the wrap shape.** Its `handle` runs *before* code, then calls `self.inner.handle(req)`, then runs *after* code, then returns. **Every middleware in this chapter** — and every middleware in real Tower — follows that exact shape.
3. **`LoggingLayer` is the factory.** Its `wrap(inner)` body is **one line**: `LoggingService { inner }`. The factory exists so the router can build a wrap without ever importing `LoggingService`.

### Stacking layers still works

```rust
let app = LoggingLayer.wrap(AuthLayer.wrap(HelloHandler));
//        └─────────── outer ───────────┘
//                         └── inner ──┘
// = LoggingService { inner: AuthService { inner: HelloHandler } }
```

Calling `app.handle(req)` walks: logging-BEFORE → auth-BEFORE → handler → auth-AFTER → logging-AFTER. Same shape, just nested.

### A mini Router is itself a Service

```rust
struct MiniRouter {
    routes: Vec<(&'static str, Box<dyn MiniService>)>,
}

impl MiniService for MiniRouter {
    fn handle(&self, req: &str) -> String {
        // assume request format: "<path> <body>" — e.g. "/hello Alice"
        let (path, body) = req.split_once(' ').unwrap_or((req, ""));
        for (p, svc) in &self.routes {
            if *p == path { return svc.handle(body); }
        }
        format!("404: {}", path)
    }
}
```

Because `MiniRouter` itself implements `MiniService`, you can write `LoggingLayer.wrap(router)` and the logging applies to **every** route below — exactly the trick the real `axum::Router` uses.

### What's missing from this mini version

| This warmup | Real `tower::Service` adds |
| --- | --- |
| `fn handle(&self, req: &str) -> String` | `async fn call(&mut self, req: Request) -> Result<Response, Error>` |
| Plain synchronous call | Async — returns a `Future`, suspends on `.await` |
| Hard-coded `&str` / `String` | A real `Request` type with method, path, headers, body |
| One associated type (`Wrapped`) | Three associated types (`Response`, `Error`, `Future`) |

That is the entire delta. The rest of this chapter is bolting those four things onto the exact pattern you just read. **`handle` becomes `call`, calls become `.await`, the return becomes `Result<Response, Error>`.** Nothing else changes.

## 1. The Worker: `HelloHandler`

```rust
struct HelloHandler;

impl Service<Request> for HelloHandler {
    type Response = String;   // the worker produces a String

    async fn call(&mut self, req: Request) -> Result<String, Error> {
        Ok(format!("Hello, {}!", req.name))
    }
}
```

Anything that implements `Service<Request>` is a worker. Its `call` method takes a request and returns a response. `HelloHandler` is the simplest possible worker — no state, one job, returns a string.

### A note on `Request`

Throughout this chapter, `Request` is a **teaching simplification** — a small struct with just enough fields to demonstrate Service / Layer / Router:

```rust
// What this book pretends Request is:
struct Request {
    method: Method,   // GET, POST, ...
    path:   String,   // "/hello"
    name:   String,   // payload data — req.name is accessed in HelloHandler
}
```

The `name` field is a shortcut for "whatever the user sent". It is not a real HTTP concept.

In **real Axum**, `Request` is not a custom struct at all. It comes from the `http` crate and is generic over its body type:

```rust
// from the `http` crate
pub struct Request<T> {
    head: Parts,   // method, URI, version, headers, extensions
    body: T,       // the body — a type parameter
}

// axum pins T to its own Body type:
pub type Request<B = Body> = http::Request<B>;
```

So a real `Service<Request>` is `Service<http::Request<axum::body::Body>>`. The body is an async byte stream — you don't access it as `req.name`; you call extractors like `Json<T>`, `Form<T>`, or `Bytes` to parse it.

| Aspect | Book's `Request` | Real Axum `Request` |
| --- | --- | --- |
| Defined where | Made up for this book | `http::Request<B>`, re-exported by Axum |
| Generic? | No | Yes — `Request<T>`, `T` is the body type |
| Fields | `method`, `path`, `name` | `method`, `uri`, `version`, `headers`, `extensions`, `body: T` |
| Body access | Direct field: `req.name` | Async stream; parse via extractors like `Json<T>` |

The Service / Layer / Router story is the same either way — once it clicks here, swapping in the real `http::Request<Body>` is a small change. Same trait, same `.call(req).await`, same wrapping. Only the field access (`req.name`) becomes a real extractor.

## 2. The Guard: `LoggingService` and `LoggingLayer`

The Guard is two pieces: the wrapper struct, and a tiny factory.

### 2.1 `LoggingService<S>` — the wrapper

```rust
struct LoggingService<S> {
    inner: S,                    // 'S' just stands for "Some Service"
}

// "For any LoggingService holding 'S', as long as 'S' is a Service..."
impl<S> Service<Request> for LoggingService<S>
where
    S: Service<Request>,
{
    type Response = S::Response; // "...my response type is whatever 'S' returns."

    async fn call(&mut self, req: Request) -> Result<Self::Response, Error> {
        // 1. BEFORE — log the incoming request
        println!(">>> INCOMING REQUEST: {:?}", req);

        // 2. PASS DOWN — hand the request to the inner worker
        let response = self.inner.call(req).await;

        // 3. AFTER — log the response
        println!("<<< OUTGOING RESPONSE: {:?}", response);

        // 4. RETURN — give the response back
        response
    }
}
```

This is what middleware really is: a wrapper whose `call` runs *before* code, delegates to `inner`, then runs *after* code.

### 2.2 `LoggingLayer` — the factory

```rust
struct LoggingLayer;   // empty marker — carries no data

impl<S> Layer<S> for LoggingLayer {
    type Service = LoggingService<S>;   // what the factory produces

    fn layer(&self, inner: S) -> Self::Service {
        LoggingService { inner: inner } // put the worker inside the box
    }
}
```

`LoggingLayer` is a tiny **factory**. The word "factory" here means exactly what it sounds like in everyday English: something whose only job is to **build** other things. It does not do the real work itself — it just produces the things that do the real work. Think *cookie cutter* (shapes dough into cookies; doesn't eat them) or *gift-wrapping machine* (wraps a present; doesn't deliver it).

| | What it is | Its job |
| --- | --- | --- |
| **Worker** | `LoggingService<S>` | *Runs* per request — logs request, calls `inner`, logs response. |
| **Factory** | `LoggingLayer` | *Produces* a `LoggingService`. Does no per-request work itself. |

The factory has exactly one method (`fn layer`) and its entire body is `LoggingService { inner: inner }` — build one wrapped service, hand it back, done.

So why is the factory separate from `LoggingService` itself? Because `Router` does not know what a `LoggingService` is — it only knows the `Layer` contract: *"give me an inner service, give me back a wrapped one."* The factory is the **adapter** that lets the router build something it has never heard of. That is why every middleware in Tower needs **two** types: the `Service` (what runs per request) and the `Layer` (what tells the router how to build it).

### 2.3 The two pieces, visualized

Once both pieces are in place, here is the picture of what each does and when:

```text
LoggingLayer  takes  ─►  some Service  (call it S)
             returns ─►  LoggingService { inner: S }

LoggingService::call  runs  ─►  BEFORE code
                              │
                              ▼  self.inner.call(req).await
                              │  (runs S — could be Handler, Router, or another middleware)
                              │
                              ▼  AFTER code
                              │
                              ▼  return response
```

Read top to bottom:

- **Setup time** (the top half) happens once, when you write `.layer(LoggingLayer)`. The factory takes some `S` and produces a `LoggingService` wrapped around it. After this, the factory's job is done.
- **Request time** (the bottom half) happens every time a request arrives. `LoggingService::call` runs the BEFORE code, hands the request to whatever `S` is via `self.inner.call(req).await`, then runs the AFTER code, and finally returns the response.

The crucial detail in the middle: `S` is not necessarily a handler. It can be a `Handler`, a `Router`, or **another middleware** — anything that implements `Service<Request>`. That is what lets you stack middlewares like `.layer(AuthLayer).layer(LoggingLayer)`: each layer just sees "some inner Service" and does its thing around it.

## 3. The Dispatcher: `Router`

Conceptually, a router is just a map from path to service.

### 3.1 Building the route table

```rust
let app = Router::new()
    .route("/hello", get(HelloHandler));
```

Step by step:

1. `Router::new()` creates an empty route table — think `HashMap<Path, Box<dyn Service>>`.
2. `get(HelloHandler)` wraps `HelloHandler` in a small adapter that only accepts the HTTP `GET` method. (A `POST /hello` will be rejected with `405 Method Not Allowed`.)
3. `.route("/hello", ...)` inserts the pair `("/hello", get(HelloHandler))` into the table.

Conceptually:

```text
Router {
    routes: { "/hello" => get(HelloHandler) }
}
```

### 3.2 The radix tree (not a flat HashMap)

In reality, Axum does **not** use a plain `HashMap`. It uses a **radix tree** (a compressed prefix tree). This matters when you have many routes that share prefixes:

```rust
.route("/users",           get(ListUsers))
.route("/users/:id",       get(GetUser))
.route("/users/:id/posts", get(GetUserPosts))
```

The tree shares `/users` once and branches:

```text
/users
   |-- (end)              -> ListUsers
   |-- /:id
        |-- (end)         -> GetUser
        |-- /posts        -> GetUserPosts
```

Path parameters like `:id` are captured during the walk and handed to the handler as extracted arguments.

### 3.3 `Router` is itself a `Service`

When `GET /hello` arrives, the router does roughly:

```rust
async fn call(&mut self, req: Request) -> Result<Response, Error> {
    let path = req.uri().path();              // "/hello"
    let service = self.routes.match_path(path)?;
    service.call(req).await                   // delegate
}
```

So `Router::call`'s entire job is **look up, then delegate**. The router is just another `Service`.

## 4. How `.layer(LoggingLayer)` wraps the router

We have a router with a route, and we have a `LoggingLayer` factory. How does the wrapping actually happen?

### 4.1 The simplest possible wrap (no traits)

Before we touch any trait machinery, here is the wrap done **by hand**:

```rust
let handler = HelloHandler;
let wrapped = LoggingService { inner: handler };
//                            ^^^^^^^^^^^^^^^^^
//                            this is the wrapping
```

That single line — `LoggingService { inner: handler }` — **is** the wrap. It is just struct construction: put `handler` into a field called `inner`. No magic.

So why don't we write that line directly in our app? Because we want the **router** to do it for us, automatically. But the router has never heard of `LoggingService`. It only knows the `Layer` contract:

> "Give me anything that implements `Layer`. I will hand you my inner service, and you must hand me back a wrapped version."

Look back at `LoggingLayer::layer`:

```rust
fn layer(&self, inner: S) -> Self::Service {
    LoggingService { inner: inner }   // <-- the same line as above!
}
```

The body is literally the manual wrapping line. **That is the only thing `LoggingLayer` does.** It is a one-method type whose method is `LoggingService { inner }` and nothing else.

### 4.2 `.layer(LoggingLayer)` triggers the wrapping

```rust
let app = Router::new()
    .route("/hello", get(HelloHandler))
    .layer(LoggingLayer);
```

When `.layer(LoggingLayer)` runs, the router does this (pseudocode of `axum::Router::layer`):

```rust
impl Router {
    fn layer<L: Layer<Self>>(self, factory: L) -> Router {
        let wrapped = factory.layer(self);   // (1) factory wraps the router
        Router::from_service(wrapped)        // (2) new router holds the wrap
    }
}
```

Step by step:

1. `factory.layer(self)` — the router hands **itself** to `LoggingLayer`'s `layer` method as `inner`.
2. Inside that method, `LoggingService { inner: self }` runs — the router is placed inside a `LoggingService`.
3. The `LoggingService { inner: router }` that pops out is bound to `wrapped`.
4. A new router is built whose inner service is `wrapped`.

After this line, `app` is conceptually:

```text
LoggingService { inner: Router { "/hello" => get(HelloHandler) } }
```

And the compiler now knows: **`S = Router`**. From here on, every place that said `S` will be replaced with `Router`.

### 4.3 Two methods named `layer` — keep them straight

The wrapping involves **two** methods called `layer`. They share a name but live in different places, and one calls the other:

| Where you see it | Whose method | What it does |
| --- | --- | --- |
| `.layer(LoggingLayer)` on a router | **`Router::layer`** (inherent method) | Receives a factory, calls the factory, stores the result. |
| `factory.layer(self)` inside that body | **`Layer::layer`** (trait method on `LoggingLayer`) | Returns `LoggingService { inner }`. The actual wrapping. |

Read as English:

> **You → Router:** "Router, please apply this factory to yourself."
> **Router → LoggingLayer:** "Factory, here is the thing you should wrap."
> **LoggingLayer → Router:** "Here is your service, wrapped: `LoggingService { inner: router }`."

## 5. What the compiler does with `S` (Monomorphization)

The trickiest piece of magic is the generic parameter `S`:

```rust
struct LoggingService<S> { inner: S }

impl<S> Service<Request> for LoggingService<S>
where
    S: Service<Request>,
{
    type Response = S::Response;
    ...
}
```

`S` is **not a value** at runtime. It is a placeholder the compiler fills in at **compile time**. This is called **monomorphization**: "mono" (one) + "morph" (form) — turning one generic blueprint into one concrete copy per concrete type used.

### 5.1 Substitution

Now that `S = Router`, the compiler textually replaces every `S` in `LoggingService<S>` with `Router`. The code it actually compiles looks like this:

**Your code:**

```rust
struct LoggingService<S> { inner: S }
```

**Compiler sees:**

```rust
struct LoggingService_Router { inner: Router }
```

**Your code:**

```rust
impl<S> Service<Request> for LoggingService<S>
where
    S: Service<Request>,
{
    type Response = S::Response;
    ...
}
```

**Compiler sees:**

```rust
impl Service<Request> for LoggingService_Router {
    type Response = Response;   // because Router::Response = Response
    ...
}
```

Two things just happened:

1. The `where S: Service<Request>` clause is **gone**. The compiler already checked once that `Router` is a `Service<Request>`. After that the constraint has done its job; it does not exist at runtime.
2. `S::Response` was resolved to `Response`, because `Router::Response = Response`. The return type is now concrete.

### 5.2 The fully expanded `call` method

This is the code that actually executes when a request arrives:

```rust
// What the compiler generates, conceptually:
impl LoggingService_Router {
    async fn call(&mut self, req: Request) -> Result<Response, Error> {
        println!(">>> INCOMING REQUEST: {:?}", req);

        // self.inner is a Router, so this call is a *direct* call
        // to Router::call — no virtual dispatch, no vtable, no boxing.
        let response = self.inner.call(req).await;

        println!("<<< OUTGOING RESPONSE: {:?}", response);
        response
    }
}
```

### 5.3 Why this matters (zero-cost abstractions)

- **No runtime cost.** `self.inner.call(req)` is a direct function call to `Router::call`. The CPU jumps straight there — no dictionary lookup, no `vtable`, no indirection.
- **No allocation.** `LoggingService<Router>` is a plain struct with a `Router` field. It lives on the stack.
- **All checks happened at compile time.** "Is `Router` actually a `Service`?" was answered before your binary was built. If you had passed something that was not a `Service`, the code would not have compiled.

In JavaScript or Python, middleware is a list of functions the server loops through at runtime: *"What's next? The logger. What's next? The auth."* That costs extra time and memory on every request. Rust's compiler does all the matching, substituting, and verifying *before* your app runs. By compile time, `LoggingService` and `Router` are fused into one specific block of machine code. You get the beautiful chained code, and it runs as fast as if you had hand-written everything.

## 6. A live request, end to end

Now boot the server and watch what happens when a user visits `http://localhost:3000/hello` with payload `{ name: "Alice" }`.

### Phase 1 — The Request Arrives (the Guard)

**1. The request hits the server.** Axum receives the HTTP request. Because the *entire* router is wrapped in `LoggingService`, the request hits `LoggingService::call` first.

> *"The Guard stops the incoming request at the front door."*

**2. The Guard logs the request.**

```rust
println!(">>> INCOMING REQUEST: {:?}", req);
```

Terminal:

```text
>>> INCOMING REQUEST: Request { method: GET, path: "/hello", name: "Alice" }
```

> *"The Guard writes the visitor's details in the logbook."*

**3. The Guard passes the request down.**

```rust
let response = self.inner.call(req).await;
```

> *"The Guard hands the request to the inner service (the Router) and pauses to wait."*

While suspended, the `LoggingService` task is **parked**. The Tokio runtime is free to work on other connections. A paused middleware is not a held thread — that is what makes Rust's async middleware cheap.

### Phase 2 — Routing (the Dispatcher)

**4. The Router finds the destination.** It takes the request, looks at the path `/hello`, walks the radix tree, finds `HelloHandler`.

> *"The Dispatcher reads the envelope, sees `/hello`, walks it over to HelloHandler's desk."*

**5. The Worker does the job.**

```rust
HelloHandler::call(&mut self, req)
    -> Ok(format!("Hello, {}!", req.name))
    -> Ok("Hello, Alice!")
```

> *"HelloHandler reads 'Alice', creates 'Hello, Alice!', hands it back to the Router."*

### Phase 3 — The Response Returns (the Guard)

**6. The Router returns the result.** Up the chain to whoever called it — the Guard.

> *"The Dispatcher hands the finished work back to the Guard at the front door."*

**7. The Guard logs the response.**

```rust
println!("<<< OUTGOING RESPONSE: {:?}", response);
```

Terminal:

```text
<<< OUTGOING RESPONSE: Ok("Hello, Alice!")
```

> *"The Guard wakes back up (`.await` is finished), looks at the string, writes it in the logbook."*

**8. The server responds to the user.** The Guard hands `"Hello, Alice!"` back to Axum, which sends it across the internet to the user's browser.

### The whole trace

Terminal:

```text
>>> INCOMING REQUEST: Request { method: GET, path: "/hello", name: "Alice" }
<<< OUTGOING RESPONSE: Ok("Hello, Alice!")
```

Alice's browser:

```text
Hello, Alice!
```

Call stack, unrolled:

```text
LoggingService::call    (BEFORE: log request)
        |
        v   self.inner.call(req).await
Router::call            (lookup /hello)
        |
        v
HelloHandler::call      (work: format "Hello, Alice!")
        |   returns Ok("Hello, Alice!")
        v   back up the chain
Router::call            (returns)
        |
        v
LoggingService::call    (AFTER: log response, return)
        |
        v
Axum                    (serialize, write to socket)
```

## 7. The big picture

Three traits, three roles:

| Trait | Role | What its `call` / `layer` does |
| --- | --- | --- |
| `Service<Request>` | The Worker | Takes a request, returns a response. |
| `Layer<S>` | The Factory | Takes a service, returns a new service that wraps it. |
| `Router` | The Dispatcher | Is itself a `Service`; its `call` looks up a path and delegates. |

Three compile-time tricks that make it fast:

1. **Monomorphization** — generic `S` is replaced with a concrete type per use site, so every `call` becomes a direct function call.
2. **No trait objects on the hot path** — Axum's tower stack is built from concrete types, so the entire middleware chain compiles to a flat sequence of inlined calls.
3. **Async `.await` parks tasks, not threads** — a middleware waiting on its inner service does not hold an OS thread, so thousands of in-flight requests share a small thread pool.

The mental model:

```text
                      compile time                          run time
┌────────────────────────────────────────┐    ┌──────────────────────────────────┐
│ Router::new()                          │    │  request arrives                 │
│   .route("/hello", get(HelloHandler))  │    │       │                          │
│   .layer(LoggingLayer)                 │ -> │       v                          │
│                                        │    │  LoggingService::call (BEFORE)   │
│ becomes                                │    │       │                          │
│                                        │    │       v                          │
│ LoggingService<Router> {               │    │  Router::call (lookup)           │
│   inner: Router { "/hello" -> Hello }  │    │       │                          │
│ }                                      │    │       v                          │
│                                        │    │  HelloHandler::call (work)       │
│ — all generics resolved,               │    │       │                          │
│   no vtables, no boxing.               │    │       v back up the chain        │
└────────────────────────────────────────┘    │  LoggingService::call (AFTER)    │
                                              │       │                          │
                                              │       v                          │
                                              │  response sent to client         │
                                              └──────────────────────────────────┘
```

Layers stack at build time, the compiler fuses them into one optimized type, and at request time each `.call(...).await` is just a direct function call that may park the task while it waits for the inner service to finish.

## Appendix — the full code in one place

```rust
struct HelloHandler;

impl Service<Request> for HelloHandler {
    type Response = String;

    async fn call(&mut self, req: Request) -> Result<String, Error> {
        Ok(format!("Hello, {}!", req.name))
    }
}

struct LoggingService<S> {
    inner: S,
}

impl<S> Service<Request> for LoggingService<S>
where
    S: Service<Request>,
{
    type Response = S::Response;

    async fn call(&mut self, req: Request) -> Result<Self::Response, Error> {
        println!(">>> INCOMING REQUEST: {:?}", req);
        let response = self.inner.call(req).await;
        println!("<<< OUTGOING RESPONSE: {:?}", response);
        response
    }
}

struct LoggingLayer;

impl<S> Layer<S> for LoggingLayer {
    type Service = LoggingService<S>;

    fn layer(&self, inner: S) -> Self::Service {
        LoggingService { inner: inner }
    }
}

// One layer wraps the whole router, so logging applies to every route below.
let app = Router::new()
    .route("/users",    get(UserHandler))
    .route("/posts",    get(PostHandler))
    .route("/comments", get(CommentHandler))
    .layer(LoggingLayer);
```
