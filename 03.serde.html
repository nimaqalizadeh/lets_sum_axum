Let's sum Axum

serde

Serde is a framework for serializing and deserializing Rust data structures.

  • Serialize = turn a Rust value into bytes you can send/store (User { name: "Alice" } → {"name":"Alice"}).
  • Deserialize = the reverse ({"name":"Alice"} → User { name: "Alice" }).

The clever part of serde is how it does this. It does not say: “here is a JSON-to-struct converter, here is a YAML-to-struct converter, here is a TOML-to-struct converter…” That would be one converter per (format × type) pair, which explodes the moment you have many of either.

Instead, serde inserts a small middle world that both sides know how to talk to. The shape of the architecture is exactly the diagram:

   ┌──────────┐         ┌──────────┐         ┌──────────┐
   │  Rust    │         │  serde   │         │  bytes   │
   │  type    │ ─────►  │   data   │ ─────►  │  in some │
   │          │         │  model   │         │  format  │
   │          │ ◄─────  │          │ ◄─────  │          │
   └──────────┘         └──────────┘         └──────────┘
        ▲                    ▲                    ▲
        │                    │                    │
   Serialize /          ~29 primitive       Serializer /
   Deserialize             "shapes"          Deserializer
   live on the type     (bool, i32, str,    live on the format
                         seq, map, struct…)

Before we look at any code, let’s nail down what each of the five labels actually means.

1. Data type

A data type is a concrete Rust type you define for your program.

#![allow(unused)]
fn main() {
struct User {
    name: String,
    age: u32,
    emails: Vec<String>,
}
}

User only exists in your code. It has fields, lifetimes, ownership rules — all the Rust-specific machinery. A JSON file has never heard of User, and User has never heard of JSON.

“Data type” here means “whatever Rust type you happen to have today” — User, Config, Vec<Order>, HashMap<String, i64>, whatever. Every program has its own zoo of these.

2. Data format

A data format is the byte-level encoding you want to read from or write to.

  • JSON: {"name":"Alice","age":30}
  • YAML: name: Alice\nage: 30
  • TOML: name = "Alice"\nage = 30
  • bincode: a compact binary blob — not human-readable.
  • MessagePack, CBOR, RON, XML, … the list is long.

A format is just a convention about bytes: which characters mean “start of object”, how strings are quoted, whether numbers are decimal or binary, etc. It has no idea what a User is either — it only knows how to encode generic things like “a string”, “an integer”, “a list of stuff”, “a key/value object”.

“Data format” stands for “whatever encoding you happen to need today”. Every program might support several of them.

3. Data model

This is the key invention. The serde data model is a small, fixed vocabulary that sits in the middle and that both sides agree on.

It is a list of about 29 primitive “shapes” that any data can be described in terms of. The big ones:

CategoryMembers
Booleansbool
Integersi8 i16 i32 i64 i128, u8 u16 u32 u64 u128
Floatsf32 f64
Textchar, str
Bytesbytes
Optionalsnone, some
Unit-ishunit, unit_struct, unit_variant
Newtypesnewtype_struct, newtype_variant
Sequencesseq, tuple, tuple_struct, tuple_variant
Maps & structsmap, struct, struct_variant

That is it. Every Rust type, no matter how exotic, is described to serde as some combination of those shapes. Every format, no matter how exotic, is told to write some combination of those shapes.

The data model is the shared language. Neither side speaks the other’s tongue, but both speak “model”.

            ┌──────────────────────┐
  Rust type ├──► "this is a struct │   ─►  JSON  writer
            │     with 2 fields:   │
            │     name: str,       │   ─►  YAML  writer
            │     age: u32"        │
            └──────────────────────┘   ─►  bincode writer
                  the data model

Why is this a win? Because of the N + M vs. N × M math:

  • Without the model: every Rust type would need to know how to write itself to every format. 100 types × 10 formats = 1000 hand-written converters.
  • With the model: each type only learns to talk to the model (100 implementations), and each format only learns to talk to the model (10 implementations). Total: 110.

You only ever cross one edge at a time. Type ↔ model, then model ↔ format.

4. Serialize — the trait on the data type

Serialize is a trait that lives on your data type. Implementing it is how the data type learns to describe itself in terms of the data model.

#![allow(unused)]
fn main() {
// simplified
pub trait Serialize {
    fn serialize<S: Serializer>(&self, serializer: S) -> Result<S::Ok, S::Error>;
}
}

Read the method out loud: “Given some serializer, describe myself to it.”

A Serialize impl for User says, in effect:

“I am a struct called User with 3 fields: name is a string, age is a u32, emails is a sequence of strings.”

It does not say “write {, then write "name":, then write "Alice"”. It never mentions JSON, never mentions YAML. It only ever mentions data-model words like struct, field, str, u32, seq.

In practice you almost never write this by hand — you derive it:

#![allow(unused)]
fn main() {
use serde::Serialize;

#[derive(Serialize)]
struct User {
    name: String,
    age: u32,
    emails: Vec<String>,
}
}

The macro generates the impl for you. Either way, the result is the same: a method that walks the type and describes it to whichever serializer it is handed. Deserialize is the mirror trait — “given some deserializer, build me from it.”

5. Serializer — the trait on the format

Serializer is a trait that lives on the format side. Implementing it is how the format learns to turn data-model words into bytes.

#![allow(unused)]
fn main() {
// extremely simplified
pub trait Serializer {
    fn serialize_bool(self, v: bool)   -> Result<Self::Ok, Self::Error>;
    fn serialize_i32(self, v: i32)     -> Result<Self::Ok, Self::Error>;
    fn serialize_str(self, v: &str)    -> Result<Self::Ok, Self::Error>;
    fn serialize_struct(self, name: &'static str, len: usize) -> ...;
    fn serialize_seq(self, len: Option<usize>) -> ...;
    // ... ~29 methods, one per data-model shape
}
}

A format crate like serde_json provides a struct (e.g. JsonSerializer) that implements every one of these methods by writing JSON bytes:

  • serialize_bool(true) → write true
  • serialize_str("Alice") → write "Alice" (with quotes and escapes)
  • serialize_struct("User", 3) → write {, remember to write } at the end
  • serialize_seq(Some(2)) → write [, remember to write ] at the end

A different format crate like bincode provides its own struct that implements the same methods but writes a compact binary form instead. Deserializer is the mirror trait — it reads bytes and calls back into the type’s Deserialize impl, telling it “I just read a string”, “I just read the start of a map”, etc.

The serializer is what turns “I am a struct with 3 fields” into actual {"name":"Alice","age":30,"emails":[...]} bytes.

Putting the five together

The moment of conversion looks like this:

#![allow(unused)]
fn main() {
let user = User { name: "Alice".into(), age: 30, emails: vec![] };
let json = serde_json::to_string(&user)?;     // "{\"name\":\"Alice\",...}"
}

What actually happens under the hood, in slow motion:

1. serde_json::to_string  builds a  JsonSerializer  (a Serializer impl).
2. It calls  user.serialize(json_serializer).
3. The derived Serialize impl on User says, in model words:
       "serializer, I am a struct called 'User' with 3 fields."
       "field 'name' is a str: 'Alice'"
       "field 'age'  is a u32: 30"
       "field 'emails' is a seq of str: []"
4. Each of those calls hits a method on JsonSerializer, which writes
   the matching JSON bytes into a buffer.
5. The buffer is returned as a String.

Notice what was not in that pipeline:

  • User never saw a { or a ".
  • JsonSerializer never saw the name User until step 3 told it.
  • Neither side imported the other.

Swap serde_json for serde_yaml and step 1 builds a YamlSerializer instead. Steps 2 and 3 do not change at all — your User still describes itself in the same model words; it is just that a different listener is now translating those words into different bytes.

That is the whole magic. The five pieces lock together like this:

   data type    ──Serialize──►   data model   ──Serializer──►   data format
                 (trait on                     (trait on
                  your type)                    the format)

Each arrow is exactly one trait. Each trait crosses exactly one edge of the diagram. Hold on to that picture — every deeper topic in serde (visitors, Deserializer lifetimes, zero-copy, format-specific attributes, custom impls) is just zooming into one of these arrows.

One type, two formats, meeting in the middle

The real serde Serializer trait has about 29 methods (one per data-model word) which is too much to show all at once. So for this example, let’s pretend serde is much smaller — its data-model vocabulary has only 3 words: “start a struct”, “here is an i32 field”, “end the struct”. That is enough to handle our Point.

#![allow(unused)]
fn main() {
// PRETEND SERDE — a tiny stand-in for the real Serializer trait.
// The "data-model vocabulary" is just these three methods.
trait MiniSerializer {
    fn start_struct(&mut self, name: &'static str);
    fn field_i32(&mut self, key: &'static str, value: i32);
    fn end_struct(&mut self);
}
}

Hold this picture in your head — it is the whole trick:

  • The trait definition is the data-model vocabulary. A fixed contract that both sides agree on.
  • The data type uses the vocabulary: it calls the methods in the right order to describe itself. It does not care who is on the other end.
  • The data format implements the vocabulary: each method body decides what bytes to produce for that model word. It does not care who called it.

So in Rust terms: the trait is the model, calling its methods is the type’s job, providing the impl is the format’s job. Neither side imports the other — they only meet through the trait. That is N + M in one sentence: the vocabulary is shared, the calling side and the implementing side are independent.

Now one data type that only knows how to describe itself in those three words:

#![allow(unused)]
fn main() {
// THE DATA TYPE — never mentions any format.
struct Point {
    x: i32,
    y: i32,
}

impl Point {
    fn serialize<S: MiniSerializer>(&self, s: &mut S) {
        s.start_struct("Point");          // model word 1
        s.field_i32("x", self.x);         // model word 2
        s.field_i32("y", self.y);         // model word 2
        s.end_struct();                   // model word 3
    }
}
}

Now two formats that only know how to turn those three words into bytes:

#![allow(unused)]
fn main() {
// FORMAT A — writes "(x=1, y=2)". Never mentions Point.
struct ParenWriter { buf: String, first: bool }

impl MiniSerializer for ParenWriter {
    fn start_struct(&mut self, _name: &'static str) {
        self.buf.push('(');
        self.first = true;
    }
    fn field_i32(&mut self, key: &'static str, value: i32) {
        if !self.first { self.buf.push_str(", "); }
        self.first = false;
        self.buf.push_str(key);            // "x"
        self.buf.push('=');                // "="
        self.buf.push_str(&value.to_string());  // "1"
    }
    fn end_struct(&mut self) {
        self.buf.push(')');
    }
}
}
#![allow(unused)]
fn main() {
// FORMAT B — writes "1,2". Never mentions Point either.
struct CsvWriter { buf: String, first: bool }

impl MiniSerializer for CsvWriter {
    fn start_struct(&mut self, _name: &'static str) {
        self.first = true;                 // nothing to open
    }
    fn field_i32(&mut self, _key: &'static str, value: i32) {
        if !self.first { self.buf.push(','); }
        self.first = false;
        self.buf.push_str(&value.to_string());  // CSV ignores the key
    }
    fn end_struct(&mut self) {
        // nothing to close
    }
}
}

Notice that each format makes different choices for the same three model words: ParenWriter::start_struct opens a (, while CsvWriter::start_struct writes nothing. ParenWriter::field_i32 uses the key ("x="), while CsvWriter::field_i32 discards it. Same vocabulary, different bytes.

Now the meeting:

#![allow(unused)]
fn main() {
let p = Point { x: 1, y: 2 };

let mut a = ParenWriter { buf: String::new(), first: true };
p.serialize(&mut a);
// a.buf == "(x=1, y=2)"

let mut b = CsvWriter { buf: String::new(), first: true };
p.serialize(&mut b);
// b.buf == "1,2"
}

Trace the first call in your head: p.serialize(&mut a) runs the one Point::serialize body. Line 1 calls a.start_struct("Point") → a.buf is now "(". Line 2 calls a.field_i32("x", 1) → a.buf is now "(x=1". Line 3 calls a.field_i32("y", 2) → a.buf is now "(x=1, y=2". Line 4 calls a.end_struct() → a.buf is now "(x=1, y=2)". The second call is identical except the methods belong to CsvWriter, so different bytes come out.

Three things to notice — they are the whole point:

  1. Point::serialize was written once. The exact same method body ran in both calls. It never mentions ParenWriter or CsvWriter, never imports them, never knows what bytes will appear.
  2. ParenWriter and CsvWriter were written without ever importing Point. They only know what to do when handed the three model words. They don’t care that those words happened to describe a Point this time — anything that calls start_struct / field_i32 / end_struct would work.
  3. The meeting happens directly at .serialize(&mut a) and .serialize(&mut b). No translator sits between them. Both sides agreed on the same three-word vocabulary, so the conversation just works.

Now add one more type — say struct Color { r: i32, g: i32, b: i32 } with its own serialize method that calls the same three model words — and both writers handle it for free, with zero changes to either format’s code. Add one more format — say an XmlWriter that turns the same three words into <Point><x>1</x><y>2</y></Point> — and Point and Color both work with it for free, with zero changes to either type’s code.

That is N + M, not N × M, in concrete form. Real serde works exactly the same way; it just has 29 model words instead of 3, which is enough to describe every Rust type you will ever want to serialize.

The other direction: two formats, one type, meeting in the middle

Deserializing is the mirror image. Bytes already exist in some format, and we want to end up with a Point. The three model words flip direction: instead of the type telling the format “here is a struct-start, here is an i32 field, here is a struct-end”, the format answers when the type asks for them.

Same trick, same vocabulary, played backwards. Our pretend data-model still has three words, but now each one is a question the type asks and the format answers:

#![allow(unused)]
fn main() {
// PRETEND SERDE — mirror of MiniSerializer. The format does the parsing
// and just hands back primitive values when asked.
trait MiniDeserializer {
    fn start_struct(&mut self);
    fn field_i32(&mut self, key: &'static str) -> i32;
    fn end_struct(&mut self);
}
}

The data type now learns to build itself from those three words — it asks for what it needs in order, and trusts the deserializer to deliver an i32 when prompted:

#![allow(unused)]
fn main() {
// THE DATA TYPE — still never mentions any format.
impl Point {
    fn deserialize<D: MiniDeserializer>(d: &mut D) -> Point {
        d.start_struct();                  // model word 1
        let x = d.field_i32("x");          // model word 2
        let y = d.field_i32("y");          // model word 2
        d.end_struct();                    // model word 3
        Point { x, y }
    }
}
}

Two formats that know how to chew through bytes and answer those three questions:

#![allow(unused)]
fn main() {
// FORMAT A — parses "(x=1, y=2)". Never mentions Point.
struct ParenReader<'a> { input: &'a str, pos: usize }

impl<'a> MiniDeserializer for ParenReader<'a> {
    fn start_struct(&mut self) {
        self.pos += 1;                     // skip the opening '('
    }
    fn field_i32(&mut self, key: &'static str) -> i32 {
        if self.input.as_bytes()[self.pos] == b',' {
            self.pos += 2;                 // skip ", " between fields
        }
        self.pos += key.len() + 1;         // skip the key and '='
        let start = self.pos;
        while self.pos < self.input.len()
            && self.input.as_bytes()[self.pos].is_ascii_digit()
        {
            self.pos += 1;
        }
        self.input[start..self.pos].parse().unwrap()
    }
    fn end_struct(&mut self) {
        self.pos += 1;                     // skip ')'
    }
}
}
#![allow(unused)]
fn main() {
// FORMAT B — parses "1,2". Never mentions Point either.
struct CsvReader<'a> { input: &'a str, pos: usize }

impl<'a> MiniDeserializer for CsvReader<'a> {
    fn start_struct(&mut self) {
        // nothing to open
    }
    fn field_i32(&mut self, _key: &'static str) -> i32 {
        if self.pos > 0 && self.input.as_bytes()[self.pos] == b',' {
            self.pos += 1;                 // skip ',' between fields
        }
        let start = self.pos;
        while self.pos < self.input.len()
            && self.input.as_bytes()[self.pos].is_ascii_digit()
        {
            self.pos += 1;
        }
        self.input[start..self.pos].parse().unwrap()  // CSV ignored the key
    }
    fn end_struct(&mut self) {
        // nothing to close
    }
}
}

Same role-reversal as before: each format makes different choices for the same three model words. ParenReader::start_struct eats a (, while CsvReader::start_struct eats nothing. ParenReader::field_i32 reads past the key ("x="), while CsvReader::field_i32 discards it. Same vocabulary, different bytes.

Now the meeting:

#![allow(unused)]
fn main() {
let mut a = ParenReader { input: "(x=1, y=2)", pos: 0 };
let p1 = Point::deserialize(&mut a);
// p1 == Point { x: 1, y: 2 }

let mut b = CsvReader { input: "1,2", pos: 0 };
let p2 = Point::deserialize(&mut b);
// p2 == Point { x: 1, y: 2 }
}

Trace the first call: Point::deserialize(&mut a) runs the one body. a.start_struct() consumes (. a.field_i32("x") skips past x=, reads 1, returns 1. a.field_i32("y") skips past , y=, reads 2, returns 2. a.end_struct() consumes ). The returned Point { x: 1, y: 2 } is bit-for-bit identical to what falls out of CsvReader parsing "1,2" — completely different bytes, completely different parsing logic, same struct at the end.

The same three observations apply, mirrored:

  1. Point::deserialize was written once. The exact same method body ran in both calls. It never mentions ParenReader or CsvReader, and has no idea what bytes were on disk.
  2. ParenReader and CsvReader were written without ever importing Point. They only know how to answer the three model questions. Anything that calls start_struct / field_i32 / end_struct in the right order would work — Color from earlier would deserialize for free.
  3. The meeting happens directly at Point::deserialize(&mut a) and Point::deserialize(&mut b). Both sides agreed on the same three-word vocabulary; the conversation just runs backwards now.

So the full picture is symmetric:

   data type   ◄──Deserialize──   data model   ◄──Deserializer──   data format
                (trait on                       (trait on
                 your type)                      the format)

Serialization walks left-to-right; deserialization walks right-to-left. The middle world — the data model with its ~29 words — is the same in both directions. That is why #[derive(Serialize, Deserialize)] gives you both for free: same vocabulary, played in opposite directions.

A confession about the example

Both examples above were kept deliberately tiny, and that hides an important asymmetry between the two sides. On purpose, every reader and writer assumed the type’s fields were exactly x and y.

The serializer side is honest: ParenWriter::field_i32 actually uses the key it is handed (self.buf.push_str(key)), so renaming Point’s fields to anything else would still produce correct output. Writing a key is trivial — you print the string you were given.

The deserializer side is fudged. ParenReader::field_i32 doesn’t really read the key from the input — it just blindly skips key.len() + 1 bytes and trusts that the digit it finds belongs to whichever field the type asked for. It only works because:

  • The fields in the input appear in the same order the type expects (x then y).
  • The keys in the input happen to have the same length as the keys the type asks for.

Rename to name / value and the parser walks off into the weeds. Reorder the input to (y=2, x=1) and the values come out swapped.

The reason is structural: writing a key is easy, reading a key is real work — you have to parse bytes, decide which field they correspond to, and cope with fields appearing in any order, missing fields, unknown fields, aliases, and so on. The mini deserializer sidestepped all of that by pretending the type’s expected order was the input’s order.

That asymmetry — easy to push, hard to pull — is exactly why real serde introduces one more concept on the deserialization side: the Visitor.

The Visitor: who decides what each piece means

In the mini example, Point::deserialize was in charge of asking for things in order:

#![allow(unused)]
fn main() {
d.start_struct();
let x = d.field_i32("x");   // "give me x next"
let y = d.field_i32("y");   // "give me y next"
}

The format had to play along. That works for our toy, but it breaks the moment the input doesn’t appear in the type’s preferred order.

Real serde flips the protocol. The format drives the loop, reading whatever happens to be next in the bytes. The type hands the deserializer a small helper — a Visitor — that says: “if you find an i32 with key x, do this; if you find one with key y, do that; if you find something I don’t recognize, here’s what to do.” The deserializer calls back into the visitor for each thing it parses.

Picture three pieces instead of two:

   data type  ──provides──►   Visitor   ◄──drives──   Deserializer
   (Point)                  (PointVisitor)            (ParenReader)

Our mini world with a visitor would look like:

#![allow(unused)]
fn main() {
// The deserializer no longer answers "give me x". It loops over the
// bytes and calls back into a visitor for each thing it finds.
trait Visitor {
    fn visit_i32_field(&mut self, key: &str, value: i32);
}

trait MiniDeserializer {
    fn deserialize_struct<V: Visitor>(&mut self, visitor: &mut V);
}
}

The type provides its own visitor — a temporary collector that knows how to absorb each field by key:

#![allow(unused)]
fn main() {
// THE TYPE — builds itself piece by piece as the visitor is called.
struct PointVisitor { x: Option<i32>, y: Option<i32> }

impl Visitor for PointVisitor {
    fn visit_i32_field(&mut self, key: &str, value: i32) {
        match key {
            "x" => self.x = Some(value),
            "y" => self.y = Some(value),
            _   => { /* unknown field — ignore */ }
        }
    }
}

impl Point {
    fn deserialize<D: MiniDeserializer>(d: &mut D) -> Point {
        let mut v = PointVisitor { x: None, y: None };
        d.deserialize_struct(&mut v);
        Point { x: v.x.unwrap(), y: v.y.unwrap() }
    }
}
}

Now the format genuinely reads keys from the bytes and tells the visitor what it found:

#![allow(unused)]
fn main() {
impl<'a> MiniDeserializer for ParenReader<'a> {
    fn deserialize_struct<V: Visitor>(&mut self, v: &mut V) {
        self.pos += 1;                       // skip '('
        loop {
            let key = self.read_key();       // parse "x", "y", or anything else
            self.pos += 1;                   // skip '='
            let value = self.read_i32();     // parse digits
            v.visit_i32_field(&key, value);  // hand it to the type
            if self.peek() == b')' { break; }
            self.pos += 2;                   // skip ", "
        }
        self.pos += 1;                       // skip ')'
    }
}
}

Three things change:

  1. Order no longer matters. (y=2, x=1) works because the visitor matches on the key, not the position.
  2. Renaming fields just works. Change Point to use name / value and update PointVisitor’s match. The reader is untouched — it parses whatever key happens to be there.
  3. Unknown fields can be handled gracefully (ignored, errored, collected) instead of corrupting the parse.

The cost is one extra concept (the visitor) and one extra trait. In return, the deserializer makes no assumptions about what the type expects.

Generalizing: Serialize and Deserialize, properly

With the visitor in hand, the two arrows of the diagram now have slightly different shapes.

Serialize is a push. The type walks itself and calls vocabulary methods on the serializer in order:

   type ──serialize()──► serializer.start_struct()
                       ► serializer.field_i32("x", 1)
                       ► serializer.field_i32("y", 2)
                       ► serializer.end_struct()

One direction. The serializer is a passive sink that does whatever it is told. That is why real serde’s Serializer trait is “just” ~29 methods — one per model word.

Deserialize is a pull with callbacks. The type hands a visitor to the deserializer; the deserializer drives the parse and calls the visitor as it finds each thing:

   type ──deserialize()──► deserializer.deserialize_struct(visitor)
                                 │
                                 ▼
                          (reads bytes, finds a field)
                                 │
                                 ▼
                          visitor.visit_i32_field("x", 1)
                                 │
                                 ▼
                          (reads more bytes, finds another field)
                                 │
                                 ▼
                          visitor.visit_i32_field("y", 2)

Two directions, one indirection. That is why real serde’s Deserializer and Visitor traits together carry many more methods than Serializer: there is a visit_* mirror for almost every serialize_*.

So the architecture is not perfectly symmetric. The middle vocabulary is shared, but the protocol differs:

                  ──Serialize──►    (push: type talks, format listens)
   data type                                                          data format
                  ◄──Deserialize──  (pull + visit: format talks, visitor listens)

Same N + M trick, same model words, same independence between types and formats — just one extra hop on the way home.

In the next sections we will do the zooming, one arrow at a time.

Going deeper: a guided tour

The mental model in the sections above is enough to read most serde code. What follows is a tour of the details that fill in around that frame — based on this walkthrough video — the small things that explain why the API is shaped the way it is.

The data model is the only contract

Each data format only needs to know about the serde data model. Each data type only needs to know about the serde data model. Neither side ever sees the other; they meet in the middle through method calls on the model’s vocabulary.

That cashes out concretely in two directions:

  • Serialize: your type projects itself into one of the ~29 model shapes. A NonZeroU64 field becomes a u64 model call. A Vec<T> becomes a seq of Ts. The Rust type, no matter how exotic, picks the closest model shape and emits that. The format on the other side decides how to write the bytes — and may even encode metadata like the struct’s name (XML does, JSON does not).
  • Deserialize: your type declares which model shapes it accepts. A NonZeroU64 field says “I can be built from u8, u16, u32, u64, …”. When the format actually parses bytes, it calls back through a visitor — visit_u32(7), visit_str("hello") — and the visitor decides what to do with each call.

The data model is not a struct of values floating between the two sides. It is a vocabulary of method calls. Bytes flow in, model-method calls come out, and a value gets built inside the visitor’s callbacks.

One type, every format — for free

This is the user-facing payoff. Put #[derive(Deserialize)] on a struct once:

#![allow(unused)]
fn main() {
#[derive(Deserialize)]
struct Config { /* … */ }
}

You can now read it from any format crate you depend on:

#![allow(unused)]
fn main() {
let c: Config = serde_json::from_str(json)?;
let c: Config = toml::from_str(toml_text)?;
let c: Config = bincode::deserialize(bytes)?;
}

Each format reads its own bytes, but every one of them funnels through the same model-method calls on your type’s visitor. Add a fourth format crate to Cargo.toml — say serde_yaml — and a fourth reader works instantly. Add a second derive(Deserialize) type and all four formats handle it. That is the N + M leverage you actually feel at the call site.

cargo expand: derive is not magic

#[derive(Serialize)] looks magical, but cargo expand lifts the curtain — it runs the macro expansion and prints the generated code. For

#![allow(unused)]
fn main() {
#[derive(Serialize)]
struct Foo { a: u64, b: String }
}

what comes out is essentially:

#![allow(unused)]
fn main() {
impl Serialize for Foo {
    fn serialize<S>(&self, serializer: S) -> Result<S::Ok, S::Error>
    where
        S: serde::Serializer,
    {
        let mut s = serializer.serialize_struct("Foo", 2)?;
        s.serialize_field("a", &self.a)?;
        s.serialize_field("b", &self.b)?;
        s.end()
    }
}
}

That is the same shape as our Point::serialize from earlier — just using real serde’s traits. Mapped onto our MiniSerializer:

Same vocabulary; the macro is a templated code generator.

The Serialize trait, in more detail

Three production details fill in around the simplified trait from §5.

The serializer is generic. Your type’s serialize method takes S: Serializer, not a concrete JsonSerializer. It cannot — must not — know whether bytes will be JSON, TOML, or anything else. Its only contract is “call the right method on S”.

Ok and Error are associated types that each format picks for itself.

  • serde_json::to_string sets Ok = String — you get JSON text back.
  • serde_json::to_writer(file, &value) sets Ok = () and writes bytes directly into the writer.

Same trait, two APIs, two Ok types. Streaming straight into an io::Write is what lets you serialize a 200 MB value without building a 200 MB intermediate String in memory. Error is a union of two failure modes: the format itself fails (IO error, value the format cannot represent) or the type called something the format cannot handle. From the caller’s perspective both are “serialization failed”.

Structs use a nested helper trait. Our MiniSerializer put start_struct / field_i32 / end_struct on one trait. Real serde splits them:

#![allow(unused)]
fn main() {
trait Serializer {
    type Ok;
    type Error;
    type SerializeStruct: SerializeStruct<Ok = Self::Ok, Error = Self::Error>;

    fn serialize_struct(self, name: &'static str, len: usize)
        -> Result<Self::SerializeStruct, Self::Error>;
    // … one method per data-model word
}

trait SerializeStruct {
    type Ok;
    type Error;

    fn serialize_field<T: Serialize + ?Sized>(
        &mut self, key: &'static str, value: &T
    ) -> Result<(), Self::Error>;
    fn end(self) -> Result<Self::Ok, Self::Error>;
    fn skip_field(&mut self, key: &'static str) -> Result<(), Self::Error>;
}
}

Three things to notice:

  • Typestate. You literally cannot call serialize_field until serialize_struct has handed you the helper. The compiler enforces the ordering — no chance to emit a field outside an open struct.
  • Recursion. serialize_field takes value: &T where T: Serialize. The serializer then calls value.serialize(serializer) internally. That is how arbitrarily nested types work: User { address: Address { … } } is just serialize_field calls bottoming out at primitive model words.
  • skip_field is how #[serde(skip_serializing_if = "…")] is implemented — it omits the field from output entirely instead of writing null.

Attributes are mechanical edits to the generated code

The #[serde(…)] attributes on fields and structs are not deep extensions to the serde data model. Each one is an instruction to the proc-macro that tweaks what the generated impl looks like.

#[serde(skip)] on field `b`
    drop the `serialize_field("b", …)` line; pass `len = 1` instead of `2`.

#[serde(rename = "user_name")] on field `a`
    change "a" to "user_name" in the generated `serialize_field` call.

#[serde(skip_serializing_if = "Option::is_none")] on field `b`
    wrap the `serialize_field` call in `if !Option::is_none(&self.b) { … }`.

#[serde(deny_unknown_fields)] on the struct (deserialize side)
    remove the `Ignore` variant from the generated `Field` enum, so unknown
    keys produce an error instead of being silently dropped.

The crate has a long list of these attributes, but the mechanism behind them is uniform. The recipe for understanding any of them is the same: write the struct without the attribute, run cargo expand, add the attribute, run cargo expand again, diff. The change is almost always one or two lines in the generated impl.

The default for deny_unknown_fields being off is a deliberate choice — forgiving deserialization lets a producer of JSON evolve over time (adding new fields) without breaking consumers that do not know about the new keys. Opt into strict mode only when you want schema enforcement.

Why the macro avoids ?

Read the expanded code closely and you will notice serde’s derive does not actually use ?. It writes out the match directly. The reason is performance.

foo()? desugars to roughly:

#![allow(unused)]
fn main() {
match foo() {
    Ok(v) => v,
    Err(e) => return Err(From::from(e)),  // implicit .into() conversion
}
}

The From::from(e) is what makes ? ergonomic — it lets the inner error type differ from the outer one and converts on the way out. But it generates code: a function call (not always inlined) and a branch the optimizer has to reason about. Multiply that by every ? in a derived impl, across hundreds of types in a real crate, and the binary grows.

In serde’s generated impls, the inner and outer error types are identical — both are S::Error. So From::from is a no-op semantically, but emitting it still costs binary size. The macro skips ? and writes the match explicitly, generating tighter code. Derive macros are not only for ergonomics; they are for picking the fastest expansion.

The 'de lifetime: zero-copy vs. owned

Deserialize has a lifetime parameter that Serialize does not:

#![allow(unused)]
fn main() {
pub trait Deserialize<'de>: Sized {
    fn deserialize<D: Deserializer<'de>>(d: D) -> Result<Self, D::Error>;
}
}

'de is the lifetime of the input bytes the deserializer is reading from. It exists because deserialization, unlike serialization, has a choice to make: do the values you build borrow from the input buffer, or do they own their bytes?

Two regimes capture the choice:

  • Input lives in memory (e.g. serde_json::from_str(s: &str)): the deserializer can hand back &'de str and &'de [u8] borrows into s. No allocation, no copy — the produced values share memory with the input. This is zero-copy deserialization.
  • Input is streamed (e.g. from_reader(file)): bytes arrive in chunks into a transient buffer that gets overwritten. The deserializer cannot hand out references into it — by the time the caller looks, the bytes are gone. Everything must be owned (String, Vec<u8>). The 'de lifetime for streaming readers is effectively 'static.

A practical consequence: from_str can deserialize a struct with a &str field; from_reader cannot. If you want both, use Cow<'de, str> — it becomes Cow::Borrowed when the deserializer can share input bytes, and Cow::Owned when it cannot.

This is the deepest reason Deserialize is heavier than Serialize. Serialization only reads &self — there is no buffer to share, no lifetime to thread. Deserialization has the extra degree of freedom, and 'de is how the type system expresses it.

The deserialization handshake

Real deserialization is a back-and-forth between the type and the format, mediated by a visitor:

type     → "the next thing in the bytes is a sequence; here is my visitor"
format   → (reads bytes) "I found a sequence, here is the first element..."
visitor  → (collects element) "ok, give me the next"
format   → "I found the second element..."
…
format   → "the sequence is over"
visitor  → "here is your final Vec<T>"

Concretely, the type calls something like deserializer.deserialize_seq(my_visitor). The deserializer reads bytes, and when it finds a sequence, calls my_visitor.visit_seq(...). The visitor pulls elements one by one and assembles the value.

Two design details worth knowing:

  • Every deserializer method consumes self. Not &mut self — self. That is the same typestate trick SerializeStruct uses. Once you have stated an expectation (deserialize_seq), you no longer hold the deserializer; control passes to the visitor. The compiler prevents “I expected a u16 and a string on the same deserializer.”
  • deserialize_* is a hint, not a contract. If you call deserializer.deserialize_bytes(visitor) but the format actually has a string in the bytes, the format may still call visitor.visit_str(...) — and let the visitor decide whether to accept it. That is why Vec<u8> works whether the source encodes bytes as a JSON array of numbers, a base64 string, or raw bytes: the visitor implements visit_* for every shape it knows how to absorb.

The choreography looks elaborate compared to Serialize, but it is exactly the asymmetry the earlier “confession” section called out: writing a key is trivial; reading and routing one is real work. The visitor + 'de lifetime + consume-self protocol is the price of doing that work safely.
